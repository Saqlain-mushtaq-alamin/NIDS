## 2. Results

### 2.1 Attribution cost (150 alerts × 28 features, 6 classes)

| Explainer | Model | Mean / alert | p95 | Total |
|---|---|---|---|---|
| TreeSHAP (exact) | XGBoost, 150 trees | **1.720 ms** | 1.796 ms | 258 ms |
| DeepLIFT | DNN (28→64→6) | **1.788 ms** | 2.203 ms | 268 ms |
| KernelSHAP | DNN (offline benchmark only) | 57.3 ms | — | 8.6 s |

Gate **G4.1** budgets 50 ms/alert for TreeSHAP: **1.720 ms, ~29× headroom.**

The plan's stated worry is that SHAP "can be slow". It can — 57.3 ms/alert for
KernelSHAP on the DNN — so the live path never uses it: alerts are explained
with TreeSHAP on XGBoost (exact and fast), while KernelSHAP is used once,
offline, inside the faithfulness benchmark where it is compared against
DeepLIFT on the *same* model. DeepLIFT at 1.788 ms/alert is what makes
per-alert neural attribution affordable.

### 2.2 Faithfulness — does the explanation match the model?

Deletion AUC on the DNN, 150 alerts, 10 masking steps, class fixed to the
model's prediction. **Lower is better**: masking the features a method claims
matter should collapse the predicted probability.

| Method | Mean deletion AUC | 
|---|---|
| KernelSHAP | 0.4265 |
| **DeepLIFT** | **0.3045** |
| Difference (paired) | 0.1221, t-test **p = 7.96e-19** |

Verdict: `deeplift significantly more faithful (paired t-test p=7.958e-19)`.

Reading this honestly:

- The two methods are compared on one model (the DNN), one dataset, and one
  baseline (features masked to 0, which for robust-scaled inputs is the
  training median). It is a statement about *this* model, not a ranking of
  SHAP against DeepLIFT in general.
- TreeSHAP is deliberately absent from the comparison: it explains XGBoost,
  not the DNN, so a deletion AUC across the two would measure the model
  difference rather than the explanation quality.
- Per-alert scores for both methods are in
  `results/phase4/faithfulness_scores.csv` so the paired test can be re-derived.

### 2.3 Tiered explanations

| Property | Value |
|---|---|
| Attack types in the run | 5 of 5 in the dataset (Botnet, BruteForce, DoS, PortScan, WebAttack) |
| Longest Tier-1 summary | **441 chars** (FR6 budget: 500) |
| Mean Tier-1 summary | 414.8 chars |
| Tier-2 payload | SHAP + DeepLIFT ranked, values, baseline, method agreement |

Example (from `results/phase4/tier1_summaries.md`):

```
HIGH CONFIDENCE ALERT — Botnet Detected (100.0% confidence) (source 10.0.0.5)

Key indicators:
  1. flow_duration: raised risk (SHAP +5.544, |weight| 5.544); observed 19.18
  2. flow_iat_mean: raised risk (SHAP +1.001, |weight| 1.001); observed 21.95
  3. syn_flag_count: raised risk (SHAP +0.523, |weight| 0.523); observed 0

Recommended Action: Isolate affected host, initiate incident response
```

Tier-1 is generated from string templates over the attribution data — no LLM —
so it is deterministic and testable, and severity / recommended action come
from reviewable lookup tables (`SEVERITY_MAP`, `ACTION_MAP`). Tier-2 carries
both attribution vectors plus a Jaccard score over the top-3 features, which
is the cheap "do the two methods agree?" signal shown under the charts.

### 2.4 Response engine (dry-run)

| Metric | Value |
|---|---|
| Alerts replayed | 150 |
| Tier split | BLOCK 59 · RATE_LIMIT 60 · LOG_ONLY 31 |
| NFR10 burst test | **10 of 15** blocked at 10/min (5 downgraded) |
| Manual rollback | succeeded |
| TTL auto-unblock | succeeded (0.4 s test TTL) |
| Firewall rules executed | **0** (`dry_run: true`) |

Three safety properties are enforced in code rather than left to the operator:

1. **Bounded blocking (NFR10).** At most 10 *new* blocks per rolling minute;
   the remainder is downgraded to `LOG_ONLY` and still recorded, so a
   mis-tuned model degrades to a log instead of locking the network out.
   Refreshing an existing rule does not consume budget.
2. **Automatic rollback.** Every block carries a TTL (300 s by default),
   reaped both by a background sweeper and on every engine call, so expiry
   does not depend on another alert ever arriving.
3. **Dry-run by default.** The command that *would* run is built and recorded
   (`netsh` on Windows, `iptables` elsewhere) but never executed, which makes
   a run fully auditable without elevated privileges.

## 3. Output contract

`scripts/run_phase4.py` writes `results/phase4/phase4_report.json` with two
layers, and the difference is the single most bug-prone thing in this phase:

- **`report["components"][<name>]`** — the per-component execution log. This is
  what the gates and the console summary read.
- **`report["dashboard"]`, `report["response"]`, `report["faithfulness"]`** —
  the bundles the UI renders. In a measured report these live *inside*
  `components`; in the demo report (which defines the layout the viewer was
  written against) they are top level.

The viewer resolves this in one place, `src.dashboard.store.bundle(report, name)`,
which prefers the nested bundle and falls back to the top level. Both writers
therefore stay free to organise their own output, and no panel has to know
which shape it was handed.

Each dashboard alert carries `alert_id`, `label`, `true_label`, `confidence`,
`severity`, `source_ip`, `session_id`, `feature_names`, `shap_values`,
`deeplift_values`, `top_features`, `tier1` and the `action` the engine took —
the two tiers are generated from the same numbers, so they cannot disagree.

## 4. Bugs found during development

Eleven, all caught by running the pipeline end-to-end rather than by reading
the code. Eight failed *silently* — they produced plausible-looking output.

| # | Bug | Symptom | Fix |
|---|---|---|---|
| 1 | **Deletion curve masked the wrong cells twice.** The top-k selector compared feature *indices* against `k`, and the fancy-index broadcast `masked[rows[:, None], ranks[:, :k]]` multiplied `(n,1)` against `(n,1,k)` into `(n,n,k)`. | Every row was masked with *other* rows' features, so the AUC was mostly noise — and it still produced a smooth, believable curve. | Rank positions instead of indices; build explicit `(row, col)` pairs. Regression test: `test_masks_each_rows_own_top_feature_first`. |
| 2 | **Report layout disagreed with the dashboard.** The driver nested bundles under `components`; the viewer read the top level. | The dashboard said "No alerts in this run" against a 150-alert report, and `alerts.csv` was written as 0 bytes. | `store.bundle()` reads both layouts; `_save_alerts_csv` uses the same rule. |
| 3 | **Tier-2 silently lost half its content.** `run_tiered` never passed `deeplift_values` to `build_alert`. | The DeepLIFT chart was absent and `method_agreement.jaccard` was always `None` — no error, just a thinner drill-down. | `tiered` now depends on `deeplift` and passes the vectors through. |
| 4 | **One IP blocked by ten alerts crashed the Response tab.** Widget keys were `unblock_<ip>`. | `StreamlitDuplicateElementKey` took down the whole panel (the lab has a single source IP). | De-duplicate blocked IPs and put the position in the key. |
| 5 | **Binary SHAP shape depended on the backend.** TreeExplainer returns `(n, f)` for a binary model; KernelExplAP wrapped around a 2-column `predict_proba` returned `(n, f, 2)`. | Callers had to special-case the kernel path — and the "kernel matches tree" test failed on the shape before it failed on the values. | `align_attributions` collapses a 2-class cube to the positive class. |
| 6 | **Response log truncated to 40 rows.** `"log": log[:40]` kept the JSON small. | The alert feed showed an action for 40 of 150 alerts; the other 110 had none. | Keep the full log (the table scrolls; completeness matters more). |
| 7 | **A 200× drop rendered as "0.0x baseline".** The ratio used `%.1f`. | An indicator line read as "no change" when the value had collapsed. | Keep three significant figures below 0.1. |
| 8 | **Paired t-test returned `nan`.** Zero-variance differences (identical methods) make SciPy answer `nan` with a divide-by-zero warning. | `nan` would have been serialised straight into the report and rendered on the dashboard. | Normalise non-finite statistics to `None`; verdict degrades to "tie". |
| 9 | **Gate G4.3 asked for attacks the data cannot contain.** Coverage was checked against the whole taxonomy. | The gate failed on missing DDoS and Infiltration flows that no lab capture contains — it could never pass. | Judge coverage against the labels present in the dataset. |
| 10 | **Emoji in Tier-1 severity.** The plan's example prefixed severity with a colour emoji. | `UnicodeEncodeError` on a cp1252 Windows console, mid-alert. | Severity is plain text; colour lives in the HTML dashboard. |
| 11 | **`use_container_width` is deprecated** in Streamlit 1.65 (renamed `width="stretch"`), but `requirements.txt` allows 1.28+. | Deprecation warnings on every render. | `_stretch()` probes the installed signature once. |

Bugs 1, 2, 3, 5 and 6 are all of the same shape: *the pipeline ran, the numbers
looked fine, and only an end-to-end check against the consumer — the metric's
own expectation, the dashboard, the chart — revealed the mismatch.* That is the
argument for driving the phase from a single script that writes the artefacts
the UI actually reads.

## 5. Deviations from the phase plan

### 5.1 Tier-1 severity is text, not emoji
See bug 10. The plan's example uses coloured emoji; this project runs on
Windows consoles whose default codec cannot encode them. The deviation is
documented in `TieredExplanation` and asserted in
`test_summary_survives_a_cp1252_console`.

### 5.2 The faithfulness comparison is KernelSHAP vs DeepLIFT on the DNN
The plan asks for "SHAP vs DeepLIFT". Comparing TreeSHAP (XGBoost) against
DeepLIFT (DNN) would measure the model, not the explanation, so the benchmark
compares two methods on the same model. TreeSHAP's latency is still gated
(G4.1) because it is the method the live alert path uses.

### 5.3 Response actions are logged, never executed
`dry_run: true` is the default in `configs/response.yaml`, `ResponseEngine`
defaults to `dry_run=True`, and nothing in the repository passes
`dry_run=False`. Building the command and recording it keeps the run auditable
without root; actually applying firewall rules is out of scope for a
research pipeline.

### 5.4 Alert provenance is joined from the lab logs
Source IPs are not in `lab_flows.csv`; they are joined from
`lab/capture_logs/session_labels.csv` by `session_id`, so the feed's
"source 10.0.0.5" is real provenance for the synthetic flows rather than an
invented address.

## 6. Limitations — what would and would not survive real data

### 6.1 The data is synthetic, and so are the explanations
Attribution patterns reflect the generator's feature relationships. A method
that ranks `flow_duration` first on this data may well rank something else
first on real traffic; nothing here validates the *quality* of an explanation
against human ground truth — only the *faithfulness* of one method relative to
another on the same model.

### 6.2 18 sessions, 6 of them in the test fold
Splitting is `StratifiedGroupKFold(n_splits=3)` on `session_id` with zero
session overlap, which is the right rule (a session in both folds leaks), but
with only 18 sessions the test fold is 6 sessions and the numbers are
sensitive to that choice. All 150 alerts come from a single source IP.

### 6.3 Deletion masks to zero, not to a learned baseline
Zero is the training median under robust scaling — plausible, but not a
baseline the model was trained against. A learned or marginal-preserving
baseline would change both AUCs; it would not obviously change their ordering,
but that is an assumption, not a result.

### 6.4 The faithfulness result is model-specific
DeepLIFT winning on this DNN is a result about this DNN at this training run
(accuracy 0.936). Retraining changes the loss landscape and plausibly the
ranking. There is no evidence here that DeepLIFT is more faithful in general.

### 6.5 No firewall was ever modified
Rollback, TTL expiry and the rate limiter are all exercised against the
in-memory bookkeeping in dry-run mode. Privileged execution, `netsh` rule
collisions, and the interaction with existing host policy are untested.

### 6.6 Out of scope
- No user study: Tier-1 text has not been shown to an analyst, and "understandable"
  is asserted only by construction (templates, ≤500 chars, named features).
- No live streaming: the dashboard reads a JSON file written by the driver.
- No adversarial manipulation of explanations (Phase 5's territory).
- No explanation-quality metric beyond deletion AUC (no infidelity,
  no sanity-check randomisation tests à la Adebayo).
